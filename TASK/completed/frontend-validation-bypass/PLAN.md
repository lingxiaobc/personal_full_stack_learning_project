# 任务方案：前端校验可绕过实验

## 任务事实与边界

- REQ-01 | 设计并执行一个本地实验，观察前端校验与后端校验分别承担什么职责。
- REQ-02 | 通过浏览器 Console 直接请求 API，证明页面校验不是安全边界，并在实验结束后恢复后端校验。
- C-01 | 实验仅访问本机 `localhost` 的前端和后端，不访问外部网站或第三方系统。
- C-02 | 不接数据库，不使用真实敏感数据，不改变认证、权限或生产配置。
- C-03 | 所有代码修改由 AI 完成，用户通过 `git diff` 审查每个阶段的变化。
- C-04 | 中间的“后端无校验”状态只允许存在于实验阶段，最终代码必须恢复后端校验。
- F-01 | 当前前端 `frontend/src/App.tsx` 会直接把姓名通过 `fetch` POST 到 `http://localhost:3000/api/hello`，尚未在提交前阻止空姓名。
- F-02 | 当前后端 `backend/src/server.ts` 已读取 `request.body.name`，并在姓名为空时返回 HTTP 400。
- F-03 | 当前前后端已经具备请求日志、响应日志和页面 Request/Response 展示，可以观察同一请求的多个层次。
- F-04 | 项目工作区已经存在 `.git`，可以使用 `git diff` 查看代码变更。
- U-01 | 浏览器当前可能运行在 `5173` 或 `5174`，实际直接请求时需要以当前页面地址和 CORS 允许列表为准。
- ASM-01 | 用户能够在浏览器开发者工具中打开 Console，并观察 Network；如果不方便，使用同一 `localhost` 地址的终端请求作为等价验证。
- 可用输入/工具/权限 | 项目源文件、正在运行的本地前后端、PowerShell、浏览器开发者工具、`apply_patch`、项目构建命令和本地 HTTP 冒烟测试；权限仅限当前工作区文件与 localhost 请求。

## 关键挑战诊断

- D-01 | 前端校验只能控制“正常页面路径”，不能约束能够直接访问 API 的调用方；如果后端缺少同等校验，非法数据仍能进入后端业务处理。因此必须保持请求体、接口和非法输入一致，只分阶段改变校验所在的位置。
- 支持链：F-01 说明页面当前能构造请求；F-02 说明后端当前有拒绝空姓名的能力；F-03 说明可以同时观察浏览器和终端；直接请求可以跳过 React 的 `onSubmit`，但不能跳过 Express 路由本身。
- 为何关键：如果先改代码再记录基线，就无法区分“页面没有发请求”和“后端拒绝请求”；如果实验后不恢复，学习项目会留下错误的安全示例。
- ALT-01 | 竞争性解释：只要页面按钮不允许提交空姓名，系统就已经安全。证伪条件：同一 API 接受来自 Console 的空姓名请求。
- ALT-02 | 竞争性解释：浏览器的跨域限制会自动替后端完成数据校验。证伪条件：在被 CORS 允许的本地页面上下文中，直接请求仍能到达接口；CORS 解决的是来源访问控制，不代替业务字段校验。

## 指导方针

- G-01 | 每一阶段只改变一个关键变量，用同一个空姓名请求对照“页面路径、无后端校验、恢复后端校验”三种结果；中间不安全状态只在本地短暂存在，并在最后一个阶段恢复。
- NG-01 | 不把实验请求发送到外部地址，不使用真实账户、密钥、个人数据或生产 API。
- NG-02 | 不把“页面不能提交”当成安全结论，也不把前端混淆、CORS 或按钮禁用当成后端业务校验的替代品。
- AI 自主范围 | 在获批的五个阶段内修改 `frontend/src/App.tsx` 与 `backend/src/server.ts`、运行构建和 localhost 冒烟测试、记录 diff 与证据；超出本地范围、需要外部写入或需要改变实验结论时先暂停。

## 近端目标与杠杆点

- O-01 | 得到一个可复现的三段对照：页面空输入在前端被拦截；直接向无校验后端发送同样的空输入得到成功响应；恢复后端校验后同一直接请求得到 400。
- L-01 | 固定请求地址 `/api/hello`、方法 `POST`、请求体 `{ "name": "" }` 和观察位置，只变更前端校验或后端校验，集中减少因果归因的不确定性。
- 杠杆失效信号 | 正常页面与 Console 请求使用了不同 payload、后端没有重新加载代码、或 CORS/端口错误让请求根本没有到达业务路由；出现任一信号时先回到对应的输入、运行状态或配置层检查。
- 暂不追求的终局 | 不扩展到登录、权限、数据库约束或生产安全体系；本轮只证明“前端验证不可替代后端验证”。

## 链式弱环节与风险

- W-01 | 这是一条严格的因果链：A-01 基线 → A-02 前端早退 → A-03 后端暂时无校验 → A-04 固定 payload 直达 API → A-05 恢复后端校验。任何上游状态不成立，后续结果都无法归因。
- 进入闸门 | A-01 必须先确认当前空姓名已经由后端返回 400；A-02 必须确认空姓名页面提交没有 Network POST；A-03 必须确认只移除了后端校验；A-04 必须记录无校验时的 200；A-05 必须记录恢复后的 400 和正常请求 200。
- 串行理由 | 每一步改变同一系统的不同安全层，不能并行，否则无法知道观察结果来自哪一次代码状态。
- 中止条件 | 出现外部地址、非预期数据、服务崩溃原因不明、代码 diff 超出两个目标文件，或恢复后的直接空请求仍为 200时立即停止并恢复已知安全版本。
- 返工层 | 前端无请求则回到 A-02 的 `onSubmit`；请求未到路由则回到端口/CORS/服务层；到达后仍状态不符则回到 A-03/A-05 的后端分支；观察记录不一致则回到 A-04 的固定请求输入。

## 假设与失败信号

- H-01 | 假设：当前浏览器页面或等价的 localhost 客户端可以向 `/api/hello` 发送固定空姓名请求。预期观察：A-04 的 Network 显示 `POST`，后端终端显示 `request.body`。最小验证：不经过表单，直接发送 `{ "name": "" }`。通过标准：A-03 状态下得到 HTTP 200；失败信号：CORS、连接失败或 HTTP 400。失败后重查：先检查端口/CORS/服务状态，再检查后端校验分支。
- H-02 | 假设：后端恢复校验后，同一请求输入的结果只因服务端校验变化而从 200 变为 400，而正常输入仍为 200。预期观察：固定空姓名直接请求为 400，正常姓名为 200。最小验证：分别发送两个请求并对照后端日志。通过标准：状态码和响应体与当前 API 契约一致；失败信号：空姓名仍为 200、正常姓名失败或构建失败。失败后重查：回到后端代码、请求体解析和服务重载层。
